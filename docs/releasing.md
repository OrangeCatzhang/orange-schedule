# 发布 Windows 安装包与更新清单

从 1.1.11 起，应用优先读取 `docs/updates/latest.json`。只有公开文件不可达时才尝试 GitHub Releases API；正常检查不访问 API。公开文件和网络仍可能受访问限制，应用内保留官方下载页入口。

## 发布顺序

1. 更新 `package.json`、`package-lock.json`、界面版本号与 `CHANGELOG.md`，运行单元和相关桌面回归，再构建 Windows 安装包。保留原应用身份、数据目录和安装标识。
2. 为安装包计算 SHA-256，生成 `SHA256SUMS.txt`。提交源码，用该提交创建对应的 `vX.Y.Z` 稳定版草稿，并上传安装包与校验文件。
3. 核对 GitHub 上传附件的名称、状态、字节数和 SHA-256 与本地一致，再公开发行版。安装包必须名为 `OrangeSchedule-Setup-X.Y.Z.exe`。
4. 在不携带登录凭据的请求中验证公开 EXE 下载与校验文件。至少核对实际下载的 EXE 内容、服务器总字节数和校验文件；仅看到发布页或上传成功提示不够。
5. 读取这个**已公开**发行版的 JSON 信息，再运行下面的命令。确认版本清单中的文件名、大小、地址与已验证安装包一致后，将清单和新的 README 下载链接提交到 `main`。
6. 直接读取 GitHub 上的公开版本文件，确认它已返回新版本，并使用应用检查器验证。文件缓存可能导致短暂延迟，不应为刷新反复高频请求。

```powershell
node scripts/write-update-manifest.cjs <已公开发行版的UTF-8-JSON文件>
```

生成工具复用应用的稳定版、安装包和官方 URL 校验，只输出检查更新所需的公开字段。**工具检查元数据，不代替第 4 步的真实下载验证。** 临时发行版 JSON 应放在 `_work/`，完成后清理。

## 清单格式与发布边界

清单沿用 GitHub Release JSON 的小型子集：`tag_name`、`draft`、`prerelease`、`published_at`、`body` 和 `assets`。只包含当前稳定版的 Windows EXE 附件。它不含密钥、用户信息或个人计划。

清单更新必须晚于安装包公开与验证。构建或上传期间保留上一个已验证版本，防止应用提示下载尚不存在的文件。清单中的版本与应用版本相同或更旧时，应用不会继续查询 API；因此每次正式发布都必须同步更新清单。

若公开文件响应为 200，但正文、版本号或安装包地址不合法，应用会停止检查并提示错误。只有网络错误、HTTP 不可用或超时才使用一次 API 备用；两个来源合计最多等待约 12 秒。官方下载页地址由主进程固定，渲染页面不能传入其他地址。
